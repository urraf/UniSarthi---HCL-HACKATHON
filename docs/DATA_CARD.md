# Synthetic Data Card (Annex E)

| Field | What we did |
|---|---|
| **Purpose** | Fake student records in the guide's fixed schema (Annex C) so the tools can answer personal questions (attendance, results, exam / supplementary / placement eligibility, what-if) without any real student data. The data must exercise every threshold in the rule registry. |
| **Generator** | `qwen2.5:7b-instruct` via Ollama (local), temperature 0.7. 6 LLM calls in total (4 groups + 2 retries), 11,353 tokens. Log: `backend/data/students/generation_log.json`. |
| **Prompts** | Verbatim template: `backend/data/prompts/students_prompt.txt`. What to generate (programmes, batches, courses, edge cases): `backend/data/prompts/generation_plan.json`. |
| **Schema enforcement** | 1) The prompt shows the exact JSON shape. 2) The LLM call uses JSON mode. 3) The reply is parsed into Pydantic models (`GenStudent`, `GenCourse`) with ranges, ID pattern `S\d{4}`, allowed results and an `attended <= held` check. 4) Extra checks: exact student IDs and courses per group, marks within internal/external maxima. 5) On any error the error message is sent back to the LLM and it retries (max 3). 6) Derived fields are computed by code, never trusted from the LLM: `total_marks = internal + external`, `active_backlogs = number of non-PASS results`. |
| **Row counts and distributions** | 32 students: 8 per programme x batch (B.Tech CSE / ECE x 2024 / 2025). 8 courses (2 per programme-semester), 64 attendance rows, 64 result rows (session 2026-MAY). CGPA 5.89-8.75 (mean by group 6.92 / 8.07 / 7.81 / 8.32). Attendance 60%-98% (mean 87.7%). Results: 54 PASS, 5 FAIL, 2 ABSENT, 3 DETAINED. Total marks 0-82 (mean 63.6). |
| **Edge cases included** | Attendance exactly at a threshold: S1001 (CS201, 80%), S1009 (CS101, 75%), S1017 (EC201, 80%). One class below: S1002 (CS201, 39/50 = 78%). Marks just below pass: S1026 (MA102, 39). ABSENT: S1004 (CS201), S1019 (EC202). DETAINED: S1005 (CS201, CS202), S1025 (EC101). Multiple backlogs: S1005, S1010. CGPA exactly at placement cut-off 6.5: S1007, S1018, S1005. |
| **Validation results** | `python scripts/validate_data.py` checks: required columns, ID format, reserved judge IDs (S9000-S9999) and `JDG` courses not used, ranges, `0 <= attended <= held`, `held > 0`, `total = internal + external`, `total <= max`, result consistent with the pass mark (read from the rule registry), ABSENT/DETAINED have external = 0, backlogs consistent with results, course programme = student programme, and that every required edge case exists. Final run: **0 violations, all 7 edge cases present** (`backend/data/students/validation_report.txt`). |
| **What the LLM got wrong** | Attempt 1 for CSE-2024 gave S1004 the wrong courses. Attempt 2 put marks above the maximum for S1001 CS201. Both were caught by the checks and fixed by retry. After that, 3 results contradicted the marks (S1003 CS201 total 56 marked FAIL, S1003 CS202 total 60 marked FAIL, S1006 CS201 total 40 marked FAIL) and were corrected by code to PASS (logged in `fixes`). The LLM also ignored two requested edge cases (S1003 should fail CS202 with 39, S1006 should fail both courses). Those edge cases are still covered by other students, which the validator confirms. |
| **Known limitations** | Attendance and results are for the same (just completed) semester, so `current_semester` is one ahead of the course semester. CGPA is not derived from the marks. Only REGULAR exam rows, no SUPPLEMENTARY history. Names are invented and may look like real names by chance. Small size (32 students). |
